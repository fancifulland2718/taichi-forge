# Taichi Forge Graph 现代化规划

本文记录 `ti.graph` / CGraph 的现状、适用边界、后端演进路线和逐阶段推进要求。
所有实现工作按本文优先级一次只推进一个问题；单个问题完成并回填 checkpoint 后停止。

## 工作流

1. 一次只处理一个问题：按优先级推进，完成后停止并等待下一步指示。
2. 先调研再拆阶段：启动问题前阅读相关代码、测试、benchmark，并对照成熟 graph 做法拆成可验证阶段。
3. 每阶段必须 checkpoint：检查编译通过性、正确性、稳定性、性能和显存占用；无法检查时记录原因。
4. 失败先修复再继续：任一 checkpoint 失败，不进入下一阶段。
5. 文档同步：阶段改动、测试命令、结果、失败与修复必须回填到对应条目。
6. 重大决策才暂停：涉及公开 API 语义、默认行为切换、跨后端资源所有权、显著显存回归或大范围架构改动时暂停。
7. 相关后端都要测试：更新涉及的后端必须通过一致性、稳定性检查。

## 当前状态

当前 Graph 是顺序 dispatch 录制与回放层，不是跨 kernel DAG 优化器。

- Python 入口：`python/taichi_forge/graph/_graph.py`
- C++ 构建层：`taichi/program/graph_builder.{h,cpp}`
- AOT 数据与执行：`taichi/aot/graph_data.{h,cpp}`
- Python 绑定：`taichi/python/export_lang.cpp`
- AOT module：`python/taichi_forge/aot/module.py`、`taichi/aot/module_builder.cpp`
- C API：`c_api/include/taichi/taichi_core.h`、`c_api/src/taichi_core_impl.cpp`

已知能力：

- JIT graph：`Graph.run()` 将 Python runtime arguments 转成 C++ `IValue` 后逐 dispatch 执行。
- AOT graph：`Module.add_graph()` 保存 graph，C API / C++ wrapper 可按名字取出 compute graph 并传 named args。
- 参数类型：scalar、matrix、ndarray、texture、rwtexture。
- 后端测试覆盖：Python graph 测试主要覆盖 Vulkan/OpenGL；AOT/C API 覆盖 CPU、CUDA、Vulkan、Metal、OpenGL 的若干路径。

已知边界：

- 没有 graph-level loop、branch、dependency DAG、跨 kernel fusion 或自动 capture。
- `Sequential.append()` 会展开 dispatch 序列，重复 substep 会增加 dispatch metadata。
- JIT 执行仍逐 dispatch 调用 kernel compile cache 和 launch。
- 运行时参数 guard 主要在 per-dispatch 上完成，graph-level exact arg set guard 仍需补强。
- DX12 graph AOT dump/load 仍有未完成标记。

## 外部成熟做法参考

- CUDA Graphs：definition、instantiation、upload、replay、update 分层；拓扑稳定时收益最大。
  参考：https://docs.nvidia.com/cuda/cuda-c-programming-guide/index.html#cuda-graphs
- PyTorch CUDA Graphs：capture/replay 依赖稳定虚拟地址，通常使用长期存活的输入/输出 tensor。
  参考：https://docs.pytorch.org/docs/2.12/notes/cuda.html#cuda-graphs
- TensorRT CUDA Graphs：dynamic shape 下按 shape recapture/cache，capture 失败时 fallback。
  参考：https://docs.nvidia.com/deeplearning/tensorrt/latest/performance/best-practices.html#cuda-graphs
- Vulkan pipeline library：Vulkan 没有通用 CUDA Graph 等价物，应偏向 command buffer、descriptor、pipeline cache/library 复用。
  参考：https://docs.vulkan.org/guide/latest/extensions/VK_EXT_graphics_pipeline_library.html
- oneDNN Graph：CPU/portable graph 更接近 op DAG、logical tensor、partition、compile/execute 分离。
  参考：https://uxlfoundation.github.io/oneDNN/dev_guide_graph_basic_concepts.html

## Python 3.10 到 3.14

仓库元数据声明 `requires-python = ">=3.10,<4.0"`，并包含 Python 3.10 到 3.14 classifier。
当前 `wheel.py-api = ""`，表示仍采用 per-CPython minor wheel，而不是 `abi3`。

规划原则：

- 短期保持 per-version wheel，所有 graph 变更至少通过当前构建 Python 的 smoke。
- CI 中为 Python 3.10、3.11、3.12、3.13、3.14 保留 import、GraphBuilder、Graph.run、AOT add/load、C API launch smoke。
- 中期将 graph runtime contract 尽量下沉到 C++/C API，Python 只做薄封装。
- 不强行把完整 pybind/numpy 绑定迁到 stable ABI；如需 abi3，只考虑极薄 loader/shim。

## 适用场景

Graph 适合：

- 固定或少量 shape-keyed 的重复 kernel 序列。
- Python launch overhead 占比高的小 kernel 链。
- MPM、fluid、sort/scan、prefix pipeline、inference-style 固定 shape workload。
- AOT 部署，特别是 C API / C++ wrapper 需要稳定 named-argument graph。
- 同一批资源反复 replay，仅数据内容变化。

Graph 不适合：

- 每步由 Python 动态控制流改变 dispatch 拓扑。
- shape、dtype、texture format、resource binding 高频变化。
- sparse SNode listgen / allocator 状态直接决定后续 grid size，且无 guard/update 支持。
- 单个 kernel 很重，host launch overhead 不是瓶颈。
- 当前主要瓶颈是 compile time 或 IR size，而 graph 只是展开更多重复 dispatch。
- 同一 graph 跨 CUDA/Vulkan/CPU 混合执行；跨后端资源所有权需要单独设计。

G0.4/G0.5 设计说明：

- 1.8.0 baseline 来源：PyPI 未提供可安装的 `taichi==1.8.0` wheel；本地 `build_env.ps1` 的 Python 3.10 环境中存在 metadata 为 `taichi 1.8.0` 的包。运行时打印的 `ti.__version__` 为 `(0, 3, 13)`，因此 benchmark 同时记录 metadata version 和 runtime version。
- 普通 MPM graph 的热退化没有通过 C++ 小补丁解决。尝试在 `CompiledDispatch` 缓存 `CompiledKernelData*` 可减少 per-dispatch lookup，但 Vulkan graph smoke 立即崩溃，退出码 3221225477；该 C++ 改动已回退，原因判断为 compiled kernel data、gfx handle 或后端状态生命周期约束尚未显式建模。
- `Graph.run()` 增加 runtime ndarray/texture args flatten 缓存，只在全量 runtime args 均为稳定 ndarray/texture 对象时复用 flattened dict；scalar/matrix 不缓存，避免值变化语义错误。该优化可小幅降低当前 Forge Python 侧开销，但不足以让普通 MPM graph 热运行超过 1.8.0。
- native graph bridge 不改变公开 API：`_append_native()` 是私有入口，用于验证固定对象、固定 native primitive sequence 的 replay 能接入 graph。它不支持 runtime arg 替换，不做跨 native/kernel DAG 优化，也不保证 AOT/C API 序列化。
- 对比 workload：`transform -> gather -> scatter`，模拟仿真/渲染中常见的属性变换、索引重排与回写链。1.8.0 baseline 只能跑普通 kernel graph；Forge native graph 使用现有 `PrimitiveSequence`，Vulkan 下可融合为 `vulkan_transform_indexed_affine_ndarray`。
- Vulkan benchmark 初次将 1.8.0 的 unsupported native modes 初始化到 Vulkan 后再 skip，child 在输出 skip 后 teardown 崩溃。修复为 native API preflight：缺 API 时不初始化后端，重跑通过。

G0.6 设计说明：

- 当前只正式支持 DSL 内预定义 native 代码进入 graph。入口仍是私有 `_append_native()`，不扩大公开 API 面；对象必须是 `NativeGraphNode` 或提供 `_as_graph_native_node()` 的 DSL 对象。
- `NativeGraphNode.compile()` 产出 `NativeGraphExecutable`，后者只暴露 `prewarm()`、`run()` 和 `debug_info`。这把“定义期 DSL 节点”和“可执行 native replay 对象”分开，为后续一般 native 代码接入时增加 eligibility guard、资源所有权、参数绑定和 fallback 留出位置。
- 当前唯一注册节点是 `PrimitiveSequence`。它覆盖已在 DSL 中定义好的 native primitive replay；不接受任意 Python `run()` 对象，避免把未建模资源生命周期或后端约束混入 graph。
- 本阶段不做过度防御性封装：依赖本地已优化 native plan 的既有正确性和资源管理，只在 graph 接入边界做类型/注册约束。
- CPU 大规模 steady 相对 1.8.0 kernel graph 仍未胜出，因此 CPU 后续应优先看 host dispatch table / 参数绑定开销，而不是把本阶段作为 CPU steady 性能完成标准。CUDA/Vulkan 已验证 native graph 可以解释普通 kernel graph 热退化的一部分来源。

### G2：重复序列与调度压缩

目标：避免将固定 substep 重复完全展开，降低 dispatch metadata、compile pressure 和 launch 编排开销。

G2 的边界：它是 graph definition / scheduling representation 优化，不是 backend replay 优化。G1 完成后，G2 只能把 repeat、AOT lazy expansion、builder allocation 这些结构信息交给 `_GraphSpec` / `_GraphInstance`；真实 CUDA Graph replay、Vulkan command buffer reuse、CPU host dispatch table 分别属于 G3/G4/G5。

各项主要目的：

- G2.1：验证 repeated `Sequential` 是否能用内部 repeat representation 降低重复 dispatch 的 runtime 编排开销。复审后已从主线裁剪，不再保留 CUDA 显式实验开关。
- G2.2：把 AOT expanded CGraph 延迟到真正需要序列化时再生成，降低 Python/JIT 构图阶段的 metadata 和 compile pressure；保持旧 AOT 格式。
- G2.3：减少构图阶段空 `_ti_core.GraphBuilder` 的 eager allocation，属于 builder-state 优化；复审后已裁剪私有开关，恢复 eager builder，避免构图小优化污染运行路径。
- G2.4：把 G2.1/G2.3 从默认路径撤回；后续 G2.S7 将其从主线移除，避免不稳定收益继续占用生产 graph 复杂度。
- G2.5/G2.6：复测 repeat/lazy 在当前架构下的实际影响，决定是否继续投入或转向 G3/G4/G5。

阶段：

1. 增加内部 repeat node 或 sequence-count representation。
2. 保持现有 Python API 行为，AOT 序列化兼容旧 graph。
3. 对 MPM88 graph 和 Vulkan graph radix sort 做 compile/metadata/运行时间对比。

G2.1 失败与修复记录：

- 第一版 Python repeat node 在 CUDA/CPU 上都把 repeat 作为 Python loop 重放，CUDA steady 未过、CPU 也退化；原因是每个 substep 都多一次 Python/C++ 边界。
- 第二版增加 `CompiledGraph::jit_run_repeated()`，将 repeat loop 下沉到 C++，CUDA steady 变为 1.45x，但 CPU steady 仍退化到 0.90x。
- 最终策略改为 CUDA-only repeat compact：CUDA 使用 repeat node + C++ repeated replay；CPU 继续使用 expanded CGraph。该策略不改变公开 API，不改变 AOT 旧格式，仅改变内部 JIT runtime representation。
- G2.1 只声明 CUDA repeat compact 完成；CPU steady 性能不是本阶段完成项，明确转入 G5，Vulkan 端按用户要求暂时冻结。

G2.2 失败、修复与追踪记录：

- 第一次 checkpoint 命令未显式设置 `PYTHONPATH=D:\taichi\python`，pytest 导入了 site-packages 中的旧包，导致 `_debug_info` 属性缺失。修正命令后同一测试组重新通过。
- CUDA substeps16 的 steady median 为 0.959x，说明小规模 repeat 场景里测量噪声和首帧成本仍能吞掉 runtime 收益；G2.2 通过点改用 repeat-heavy substeps64，并把首帧成本转交 G3。
- Vulkan substeps64 已按用户要求追踪：build+first 1.11x、显存更低，但 steady 0.81x。该结果不阻断 G2.2，但必须保留到后续 Vulkan 专项中解释。

G2.3 失败、修复与追踪记录：

- 尝试把 `CompiledGraph::jit_run_repeated()` 改成单次 `Graph.run()` 内预解析 compiled kernel data，再重复 launch；正确性通过但 CUDA MPM steady 从 1.8.0 baseline 的 0.96x 进一步掉到 0.64x，已回滚。结论：不在 G2 引入 C++ launch-loop 结构变化，避免破坏现有调度时序。
- 第一轮 G2.3 benchmark 继承了 pytest 的 `PYTHONPATH=D:\taichi\python`，可能污染 vanilla baseline；所有用于记录的性能 checkpoint 均用 `Remove-Item Env:PYTHONPATH` 后重跑。
- lazy runtime builder 在 heavy MPM 中只改善 graph build，不改善 steady；因此 G2.3 的运行边界明确为 dispatch/graph overhead 占比较高、CUDA repeat-first/repeat-heavy 的场景。CPU steady 仍属于 G5，Vulkan steady 仍属于 Vulkan 专项。

G3.1 设计与边界记录：

- 真实 CUDA Graph replay 不能在 Python 层假装完成：当前 C++ `CompiledGraph::jit_run()` 每个 dispatch 都经 `Program::compile_kernel()` 缓存和 `Program::launch_kernel()`，而 CUDA Graph capture/replay 需要在该层以下接入 CUDA driver graph API。
- G3.1 guard 的稳定子集先限定为单个 expanded CGraph；native node 已正式化并通过 native replay 接入，G2 repeat node 暂不混入 CGraph capture，以免把 repeat representation 与 backend replay 两个实验变量叠在一起。
- 对无 runtime args 的 field/SNode 图，后续 G3.2 可以优先尝试 stream capture + instantiate + replay，因为参数更新语义最简单，MPM+render 就属于应优先验证的复杂场景。
- 对 ndarray/scalar runtime args，后续必须先定义 shape/key/update 语义，避免 capture 后把旧 scalar 或旧 ndarray 指针固化到 graph exec 中；这也是本阶段没有直接启用真实 replay 的原因。

G3.2 设计与边界记录：

- native graph 已经是 DSL-defined backend replay，因此本阶段不再重复实现 CUDA native 调度，而是把已有 `NativeGraphExecutable.prewarm/run/debug_info` 安装到 G1 的 backend executable 槽里。
- 只默认接管 CUDA native-only graph：这类 graph 没有 runtime args，资源对象在 DSL native sequence 中已绑定，避免 CGraph capture 的 scalar/ndarray update 语义风险。
- mixed native+CGraph 暂不进入 G3.2，因为调度顺序、同步边界和资源所有权需要显式建模；后续应先做只读 guard，再考虑串接 native replay 与 CUDA Graph capture。
- MPM+render 复杂场景目前不含 native primitive，所以 G3.2 不会改善 G3.1 记录的普通 CGraph 热退化；下一阶段仍需做 C++ CUDA stream capture/instantiate/replay。

G3.3 设计与边界记录：

- 普通 CUDA CGraph 不能直接通过 `CompiledGraph::jit_run()` 外层 stream capture 实现：`runtime/cuda/kernel_launcher.cpp::launch_llvm_kernel()` 当前每次 launch 都会分配 device result buffer、上传 host arg buffer、释放 device arg/result buffer，并且这些资源操作不属于一个稳定的 backend-neutral graph executable resource package。
- 私有 stream capture 即使能 instantiate，也会因为 `ti.sync()` 只同步当前默认 stream 而产生假收益；强制同步后又暴露 runtime context / arg buffer 生命周期问题。
- 因此 G3.3 暂停在安全 fallback：C++ 入口存在但返回 false，Python backend executable 通过 G1 fallback 回到 dispatch loop。继续 G3 前需要一个重大设计点：正式的 graph executable resource package，至少要把 compiled kernel handles、RuntimeContext、device arg buffer、device result buffer、stream ownership 和 capture-safe allocation/free 生命周期统一归 backend executable 管理；已裁剪的 CUDA persistent registry 不再作为前置层。

G3.4 设计与边界记录：

- 本阶段只正式化最小 persistent launch package：复用 device arg/result buffer，仍由现有 `launch_llvm_kernel()` 顺序 launch 每个 offloaded task；它不是 CUDA Graph instantiate/replay，也不改变 `CompiledGraph::jit_run_cuda_graph()` 的安全 fallback。
- 启用条件刻意保守：仅 opt-in，且遇到 host external array transfer 时回落旧路径，因为该路径需要临时 device allocation 和 host copy-back，不适合进入当前复用 package。
- 为保持架构简洁，本阶段不把状态放进 `KernelLauncher` 类布局，而是放在 `.cpp` 内部 registry；这是为了先验证性能和生命周期边界。若后续要默认开启或连接 CUDA Graph capture，必须把 registry 下沉为 graph-instance-owned launch package，并显式建模 stream ownership、capture-safe allocation/free、context/reset 生命周期。
- 当前性能结论是“小正但不够”：persistent launch 降低了普通 CGraph 的一部分 malloc/free/arg buffer 周转开销，但 258-dispatch MPM+render 仍主要受现有 per-dispatch launch/compile-cache/runtime 调度路径约束；下一阶段应继续把该 package 接到真实 CUDA Graph capture/replay，或转向能减少 dispatch 次数的 G6 小范围 optimizer。

G3.5 设计与边界记录：

- IMA/访问冲突的直接原因不是 graph replay 概念本身，而是 capture 把短生命周期状态固化了：driver wrapper 布局、stream ownership、`RuntimeContext` 指针、device arg/result buffer、host/device copy-back 都还没有统一归 graph instance 管理。
- S11 后 replay opt-in 已从主线删除：没有真实 capture/replay 后端的 CUDA CGraph fallback 不再作为生产路径或诊断路径保留；需要重新引入时必须先有 backend executable resource package 和稳定的 graph-owned launch context storage。
- 已裁剪的 persistent package 是 CUDA-only device buffer cache，不是可复用的 graph-owned executable state；它不应继续作为架构基座。下一阶段如果继续 CUDA Graph capture，应先定义 backend executable resource package，再建模 stream 与 reset/finalize 清理；否则任何“能跑一次”的 capture 都可能只是隐藏 IMA 或 stale pointer。

G3.6 设计与边界记录：

- G3.6/G3.7 的生命周期实验已由 G3.S10 裁剪：persistent package 曾用于定位 reset/scope 边界，但不再保留在主线。
- 统计接口只作为内部测试/诊断使用，用于验证 run 后确实创建 package、reset 后归零；不作为公开 API contract。
- S10 后默认路径不再读取 persistent env，也没有 graph scope wrapper；保留的结论是：这类 CUDA-only buffer cache 即使局部有 runtime 正收益，也不适合作为现代 graph 架构基线。

G3.7 设计与边界记录：

- G3.7 的 graph-scope token 证明了“资源所有权必须归 graph/backend executable 生命周期”这一点，但 `.cpp` registry 与 Python scope wrapper 已删除。后续如果恢复类似能力，必须作为正式 backend executable resource package，而不是隐藏全局 registry。
- G3.S3 明确保留 runtime 有收益的 hot-path 修复：避免每个 CUDA dispatch 复制 launcher context。未能证明收益的 scope-gated env probe 已撤回，避免保留非必要语义变化。
- G3.S4 说明并非所有“少容器”改动都有收益：移除 `device_ptrs` 中转 map 的 probe 在 MPM graph 中退化，已撤回。后续仍以复杂 workload runtime 数据决定保留，而不是凭架构直觉。
- G3.S5 进一步确认热路径 micro-change 也必须以 workload A/B 为准：`OffloadedTask` 引用迭代看似减少复制，但同环境 Forge-only 退化，已撤回，不为语法洁净保留负收益改动。
- G3.S6 的调用次数画像给出后续减法优先级：当前 graph/direct/1.8.0 graph 都是每帧 258 次 C++ dispatch 入口，说明 Forge graph 还没有减少 `compile_kernel` / `launch_kernel` / `launch_llvm_kernel` 调用数。下一步低风险项是 graph 实例级 compiled dispatch cache，目标把每帧 258 次 `compile_kernel` 和 258 次 `register_llvm_kernel` 降到 0，但仍保留 258 次 `launch_llvm_kernel`；大收益项仍是真实 CUDA Graph replay，把 258 次 `launch_llvm_kernel` 降到 1 次 graph launch 或 0 次旧路径调用，但这依赖 graph-owned launch context storage。
- G3.S7 完成第一层减法：实测把 CUDA graph measured repeats 中的 `Program::compile_kernel` 从 258/frame 降到 0/frame，并带来复杂 MPM+render no-profile steady 1.074x vs 1.8.0 graph。`register_llvm_kernel` 与 `launch_llvm_kernel` 仍为 258/frame；直接 handle launch 和 register-skip probe 已因真实 IMA/heap corruption 撤回。第二层应转向 graph-owned launch/replay 或更小范围的 launch package 生命周期设计，而不是继续在现有 `launch_llvm_kernel()` wrapper 上裸跳层。
- G3.S8 第二层 micro probe 说明：继续削 `LaunchContextBuilder` 或 arg-vector 这类 C++ 小对象开销不稳定，甚至会放大 outlier；在当前 258/frame launch 数不变的前提下，这类改动不是主收益来源。后续第二层若继续推进，应直接围绕“减少 `launch_llvm_kernel` 次数”或“graph-owned CUDA launch package + capture-safe storage”设计，而不是保留无实测收益的微调。
- G3.S9 稳定化修正：clean build 后 prepared dispatch cache 不通过 runtime-first checkpoint；虽然能把 `Program::compile_kernel` 降到 0/frame，但复杂 workload median 和 `launch_llvm_kernel_total_s` 都退化。该路径还强绑定 CUDA，不适合作为现代 graph 架构基线，因此已从代码中移除。G3.S10 进一步删除 persistent launch scope/token，避免留下 CUDA-only registry 作为伪 graph-owned state。
- 性能结论仍保守：当前默认 CUDA graph 在复杂 MPM+render steady 指标上仍有波动，prepared cache 已移除而不是保留为 opt-in；首帧/build+first 仍慢，且 register/launch 调用数没有减少。下一步收益必须来自真实 CUDA Graph instantiate/replay、graph-owned launch package，或减少 dispatch 次数的 optimizer。

G3.8/G3.9 设计与边界记录：

- G3.8 的最小 no-runtime-arg capture 失败说明：即使没有 runtime args，当前 `launch_llvm_kernel()` 仍会在 capture 内经过短生命周期 launch context、device arg/result buffer、stream/global CUDAContext 切换和 allocator/free 语义；这些状态没有统一归入 graph instance 生命周期前，stream capture 得到的 graph exec 不可接受。
- stable host `RuntimeContext` 只是必要条件之一，不是充分条件；失败仍出现在后续 CUDA driver 调用和 teardown，说明还需要 graph-owned launch package 管住每个 offloaded task 的 host/device 参数存储、stream ownership、capture-safe allocation/free，以及 reset/finalize 清理顺序。
- G3.9 的 runtime arg update guard 不应先实现成 Python 层签名检查后强行进入 C++ capture；它的正确顺序是先有稳定 G3.8 replay 基座，再定义 ndarray/scalar/texture 的 resource key、shape guard、update/recapture/fallback 策略。
- 因此本轮停止在 G3.8 checkpoint：保留 opt-in fallback 和 debug tracking，撤回危险 driver wrapper，不把失败 capture 数据作为性能收益；G3.9 只记录目标和依赖，不启动实现。
- 参考 Warp 后的补充结论：Warp 的有效经验不是简单缓存某个句柄，而是把 stream、capture id、graph allocations、temporary allocations、deferred free/destroy 和 module/function lifetime 一起放进 runtime 状态。Forge 的小型 `CUfunction` cache 探针没有 runtime 正收益或破坏 reset 稳定性，因此不保留；若继续 CUDA replay，应直接做 graph-owned launch package，而不是继续在现有 launch path 上叠小 cache。

- 待后续裁剪候选：暂无新的主线裁剪候选；下一步应转向正式 backend executable/resource package 设计，或转向能减少 dispatch 次数的 graph optimizer。

### Graph 架构审查（2026-05-29）

当前分层：

- Python definition layer：`GraphBuilder` / `Sequential` / `_AOTGraphBuilderPlan` 负责记录 dispatch 和 AOT 兼容展开；repeated `Sequential` 在 runtime 主线里始终展开到普通 CGraph，不再有 repeat/lazy 环境变量改变运行形态。
- Runtime spec/instance layer：`_GraphSpec` 描述节点和能力，`_GraphInstance` 绑定当前 runtime/config，负责 fast path、native replay、backend executable、prewarm 和 debug info。G5.9 后不再保留 fallback 注入状态；这一层继续作为后端接入口。
- Backend executable layer：当前只有 native replay 是实质收益路径；普通 CGraph 仍调用 C++ `CompiledGraph::jit_run()`，不再保留 CUDA candidate / CGraph replay fallback-only 分支。
- C++ execution layer：`CompiledGraph::jit_run()` 仍逐 dispatch 走 `Program::compile_kernel()` / `launch_kernel()` / `register_llvm_kernel()` / `launch_llvm_kernel()`。profile 证明当前复杂 graph 仍是 258/frame C++ dispatch，因此普通 CGraph 还没有现代 graph runtime 的核心收益。

审查结论：

- 架构健康项：G1 的 spec/instance 边界、native replay 接入、AOT lazy plan 和 benchmark/debug metadata 都值得保留；G5.9 已把 fallback 注入协议从生产路径移除。这些边界能承接 CUDA/Vulkan/CPU 的后端实现，而不是把优化散在 Python wrapper 或 CUDA runtime 全局状态里。
- 架构有损项已裁剪：persistent launch registry、prepared dispatch cache 和 launch micro probes 都属于 CUDA-only 旁路，不能作为跨后端 graph 语义承载层。
- 最大缺口：普通 CGraph 没有 backend executable representation。当前 `_CompiledCGraphNode` 只是 AOT C++ graph 的薄包装，缺少 per-backend resource package、kernel handle lifetime、runtime arg update guard、stream/command buffer ownership。
- 运行边界：graph 适合拓扑稳定、重复运行、dispatch 数量多且 runtime args 形状稳定的场景；不适合每帧拓扑变化、频繁换 ndarray/texture 资源、一次性 graph、或后端资源生命周期尚未稳定的 capture 路径。
- 下一步优先级：不要再做 CUDA-only 小 cache；先选一个正式后端 executable 原型。CUDA 方向必须减少 `launch_llvm_kernel` 调用数或形成 graph launch；Vulkan 方向必须落在 command buffer/descriptor/resource state 生命周期；CPU 方向应是 host dispatch table / compiled plan，而不是 repeat Python/C++ wrapper。

G4.2 生命周期抽取记录：

- 本阶段只把已验证的 native replay 范式正式化：command buffer 由 cache entry 持有，提交时由 `VulkanStream` 的 submitted command buffer fence/ref tracking 继续管理 pending 生命周期；recorded command buffer 的 pipeline/descriptor/buffer/image 引用仍通过 `DeviceObjVkCommandBuffer::refs` 保活。
- 暂不把普通 CGraph 接入 command replay，原因是 `GfxRuntime::launch_kernel()` 的 args/ret buffer、descriptor set、texture layout、pending barrier、ctx buffer pool 和 sparse list 状态仍需要 graph-owned resource package；继续从 `CompiledGraph` 或裸 `CompiledKernelData*` 侧绕过会重复 G4.1 的生命周期风险。
- 下一阶段 G4.4 应在 `GfxRuntime` 侧设计普通 CGraph 的 Vulkan replay packet：先支持拓扑稳定、runtime ndarray 资源稳定、无 host readback/texture/storage image/sparse topology mutation 的 dispatch 序列；miss/资源变化回落普通 `launch_kernel()`，命中时复用 command list 或 descriptor/resource set package。

G4.3 固定开销裁剪记录：

- 保留项：去掉冗余 `flush_if_pending()`、单 entry last-key cache、静态空 waits、进程内 replay env gate。这些减少命中路径层级和小对象状态，不改变 command buffer/descriptor 生命周期。
- 不继续投入项：native replay micro tweak 的收益已经进入噪声区，普通 MPM CGraph 仍明显慢于 1.8.0；后续收益不应继续围绕 native replay wrapper，而应转向 `GfxRuntime` 普通 CGraph dispatch 序列的 command/resource package。
- 下一阶段改名为 G4.4：普通 Vulkan CGraph replay/resource package 原型。准入边界应明确排除 host readback、texture/storage image、sparse topology mutation 和资源 shape/alloc 变化；命中目标是减少 130/frame 级别的 per-dispatch `launch_kernel()`/descriptor binding 固定开销。

G4.9 Vulkan backend-owned graph replay package（完成/保留，2026-05-30）：

- 调研与迁移原则：参考 Vulkan 成熟做法时，不再寻找 CUDA Graph 的一一对应物，而是迁移 command buffer / descriptor / pipeline state 可复用的思想；结合本代码库 G4.6 事件分解，优先切断每帧 34 dispatch 的 `launch_kernel()`、resource binding 和 command recording 固定链路。生命周期按 backend runtime 管理，不能把 Vulkan command/resource 状态塞进 `CompiledGraphJITCache`。
- 阶段 1，eligibility + dispatch packet：`CompiledGraph::jit_run_cached()` 新增 Vulkan 尝试入口，内部生成 `gfx::GfxRuntime::GraphDispatch`，只传 `KernelHandle` 与本次 `LaunchContextBuilder`；kernel handle 通过 `gfx::KernelLauncher::get_or_register_kernel()` 获取。准入边界为 release config、多 dispatch、Vulkan GFX runtime、无 profiler、无通用 dispatch cache。单 dispatch graph 直接回既有路径，避免 arg-binding 类 workload 被 replay ring 和 key 构造拖慢。
- 阶段 2，runtime-owned resource replay slots：`GfxRuntime` 按 graph cache key 持有 `GraphReplayState`，每个 state 有 8 个 slot，slot 内持有稳定 args buffer、resource set、recorded command list、completion token 和资源 key。key 只建模 runtime ndarray 的 device allocation、offset、bytes 与 access；当前排除 ret buffer、argpack、texture/RWTexture、storage image、listgen、chunked array、sparse topology mutation 与 host readback。第一版曾把 state 放进 `CompiledGraphJITCache`，teardown 时出现生命周期风险，已改为 `GfxRuntime` 析构时先同步再清空 replay states。
- 阶段 3，command replay 命中路径：miss 时用 slot-local args buffer/resource set 录制完整 command list 并提交；hit 时只更新 slot-local args buffer，然后直接提交 recorded command list。slot 的 completion 未完成时不复用该 slot，转为重新录制，避免覆盖仍在 GPU 使用的 args/resource。该路径只作为 Vulkan graph backend executable 原型，不改变公开 Python API 和 AOT 序列化格式。
- 阶段 4，graph-level buffer barrier pass：在一次 graph record 内按 dispatch tracking runtime ndarray 写集合，在后续读写前插入 buffer barrier，并在末尾补齐写后 barrier；texture/storage image 与 sparse/listgen 等未建模资源继续不进 replay。该阶段先保证复杂 MPM graph 的正确性和稳定性，不做跨 kernel fusion。

G4.14 Vulkan descriptor/resource package staticization audit（拒绝作为 steady runtime 项，2026-05-30）：
