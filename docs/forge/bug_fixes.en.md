# Taichi Forge Bug Fixes

## Fixed Issues

| Area | Fix | User impact |
| --- | --- | --- |
| ArgPack lifetime | Fixed premature Python GC of `ti.types.argpack(...)` objects while GPU kernels may still use their runtime allocations. See upstream [#8788](https://github.com/taichi-dev/taichi/issues/8788). | Long-running simulations, reinforcement-learning environments, graph replay, and high-frequency kernel launch loops no longer hit random crashes from ArgPack lifetime races. |
| ArgPack values on Vulkan | Fixed stale `ti.types.argpack(...)` reads on the Vulkan backend after repeated launches or updates to an existing ArgPack object. | Simulation, material, camera, and solver parameters passed through ArgPack now behave consistently across CPU, CUDA, and Vulkan without requiring user-side synchronization. |
| Vulkan small-integer fields | Fixed SPIR-V support for `ti.u8` / `ti.i8` / `ti.u16` / `ti.i16` fields on devices that expose the required Vulkan storage capabilities. See upstream [#8758](https://github.com/taichi-dev/taichi/issues/8758). | Color buffers, masks, voxels, compressed state, and image-like data can use small integer storage on the Vulkan backend. |
| Vector / Matrix ndarray release | Fixed runtime memory not being released when `ti.Vector.ndarray(...)` or `ti.Matrix.ndarray(...)` objects are destroyed. See upstream [#8763](https://github.com/taichi-dev/taichi/issues/8763). | Rendering staging buffers, particle buffers, and test loops that create temporary ndarrays no longer keep growing device memory. |
| Dense native paths after sparse SNode trees | Fixed CPU/CUDA native dense field paths, including `from_numpy()` / `to_numpy()` and native dense algorithms, after a sparse `pointer.bitmasked` tree had already been created. | MPM-style solvers can create sparse grids and then initialize or process later dense scalar, vector, or matrix fields without access violations or invalid CUDA copies. |
| PrefixSumExecutor warning | Fixed the AST warning caused by Python float division inside the internal scan kernel. See upstream [#8777](https://github.com/taichi-dev/taichi/issues/8777). | `ti.algorithms.PrefixSumExecutor`, compact, bucket builder, and other scan-based paths avoid a misleading compile warning. |
| GGUI `set_image()` staging | Optimized `canvas.set_image()` so CUDA/Vulkan Taichi field and ndarray images are packed to RGBA8 on the device, and contiguous host `uint8` RGBA NumPy images use the direct host RGBA8 path. | Rendering and simulation visualization avoid the old per-frame device-to-host staging round trip on the common device-image path. Packed `u32` display frames remain available for producers that already write final RGBA8 pixels. |
| GGUI event pump | Reduced headed GGUI mouse enter/leave overhead by preventing the ImGui GLFW backend from rewriting the native cursor every frame, and added `poll=False` to `Window.get_event()` / `Window.get_events()` so async render loops can drain events without a second `glfwPollEvents()`. | Async simulation/rendering loops can keep `window.show()` as the only per-frame event pump while preserving the legacy default behavior of event-reading APIs. |
| GGUI empty ImGui frames | Balanced the ImGui frame lifecycle when a frame has render work but no ImGui widgets: GGUI now calls `EndFrame()` for empty UI frames and skips backend ImGui draw submission. | Headed and offscreen GGUI loops can alternate widget and non-widget frames without hitting ImGui's "Forgot to call Render() or EndFrame()" assertion, while empty UI frames avoid unnecessary ImGui render commands. |
| GGUI hidden-window submission | Fixed a Windows/Vulkan crash that could happen when a hidden window completed one `canvas.set_image()` / `window.show()` frame and then released window resources. | Headless rendering, CI visualization smoke tests, and simulation screenshots can safely use `show_window=False`. |
| Vulkan async GGUI queue submission | Externally synchronized `vkQueueSubmit` and `vkQueuePresentKHR` by the actual `VkQueue` handle, and protected per-thread stream creation and submission tracking. Stream synchronization now waits only the fences of submissions made by that stream, without holding the queue lock; profiler query results are tied to the fence of the successful submission that recorded them. Host access to a shared fence is also serialized. | A Python worker can continuously submit Vulkan kernels while the main thread uploads and presents GGUI frames without racing host access to a shared queue. Synchronizing one stream no longer makes unrelated queued compute, graphics, or present work wait for a queue-wide idle. Applications do not need a coarse Python submission lock or an extra `ti.sync()` solely for queue safety; application-owned simulation/display data still needs an explicit producer-consumer protocol. |
| CUDA target resolution and cache isolation | Separated the physical CUDA device capability from the LLVM NVPTX code-generation target. The resolver uses the processor/PTX pairs supported by the bundled LLVM, selects the native `sm_120` / PTX 8.7 pair for a CC 12.0 device, and otherwise selects the highest compatible compiler target. CUDA offline-cache keys now include that resolved target. | Newer GPUs no longer report or compile as the old `sm_86` fallback when the bundled compiler supports their native target. A future GPU whose target is not yet supported safely uses the newest compatible target instead, and cannot reuse PTX cached for a different target. The public `cuda_compute_capability` query now reports the actual device capability. |
| CUDA contention and allocator diagnostics | Added sampled, non-blocking contention counters around the existing CUDA Driver and context locks, plus counters for async-pool allocation/free calls and their synchronous fallbacks. The `cuda_driver_telemetry_stress.py` runner exercises 1/2/4 Python submitters with an atomic result check. | Synchronization behavior is unchanged: these counters collect evidence before any lock-topology change. They show whether a workload actually contends on host locks and whether temporary allocations use the async pool or fall back safely, without adding per-call clock reads or an extra `ti.sync()`. |
| CUDA void-kernel launch allocation | Made the CUDA LLVM launcher allocate its device result buffer only when a kernel return value or a host-array transfer actually needs it. Void kernels operating only on Taichi fields do not allocate that buffer. | Ordinary field-only CUDA submissions no longer create one stream-ordered async allocation/free pair per launch. Return values and host-array copies retain their existing result channel and ordering; this adds no persistent cross-invocation buffer, no extra synchronization, and no change to graph capture/replay ownership. |
| CUDA allocator capability and mapping lifecycle | Initialized CUDA memory-pool capability state and require both a CUDA 11.2+ driver and device memory-pool support before selecting async allocation. Internal CUDA buffer mapping now rejects invalid or repeated map calls and reliably releases host staging state during unmap, deallocation, or reset. | Older drivers and unsupported devices use the established synchronous allocation fallback instead of selecting an API from uninitialized state. Normal field and ndarray workflows retain their public API and synchronization semantics. |
| CPU/CUDA allocation identity and lifetime | Replaced the mutable CPU/CUDA allocation tables with generation-checked, pointer-stable internal records. Every allocation, copy, map, and readback now validates the owning device and an overflow-safe whole range while retaining a short operation lease; stale, released, wrong-device, and out-of-range handles are rejected. CUDA async allocations retain their allocation stream for stream-ordered release, and each allocation owns its mapping state. | Concurrent host callers no longer race vector reallocation or access a recycled allocation record. This does not serialize conflicting application writes or create cross-stream data dependencies: applications must still express ownership and ordering for shared fields and buffers. |
| Vulkan-CUDA external-memory lifetime | A Vulkan device now advertises exportable external memory only when both the Vulkan external-memory base and the platform handle extension are enabled. The interop cache is keyed by Vulkan allocation generation and is released on allocation/device teardown; interop copies complete their CUDA work before the imported mapping can be recycled. | Direct Vulkan-CUDA buffer copies on supported Windows/Linux devices no longer retain stale imported mappings across allocation reuse or teardown. Devices without a platform export extension safely use a synchronous host-staging fallback instead of calling an unavailable handle-export function. The conservative completion applies only to this interop transfer path; ordinary CUDA kernels and Vulkan submission remain asynchronous. |
| Vulkan pipeline-cache persistence | Reworked pipeline-cache snapshots to copy a complete, size-consistent blob and retry a transient `VK_INCOMPLETE`. A rejected or incompatible persisted cache is discarded and rebuilt from an empty cache instead of aborting initialization. | A stale `rhi_cache.bin`, including one left after a driver or device change, becomes a cache miss rather than a startup crash. Cache data remains an optional optimization and does not change kernel results. |
| Vulkan GGUI swapchain results | Explicitly classify successful, suboptimal, out-of-date, device-lost, and other present/acquire results. Suboptimal or out-of-date presentation schedules normal swapchain recreation on a later window frame, outside the Vulkan queue lock. | Resize, display-mode, and WSI transitions can drop a transient GGUI frame instead of presenting against stale resources. Device loss is reported once and is terminal for the current Vulkan program/window; recreate the program/window after addressing the underlying driver or device failure. |
| CPU concurrent jobs, native primitives, and cached graph replay | CPU scheduler submissions own separate callback, context, completion, and exception state. Concurrent producers enter a fair FIFO queue; one active job uses its requested bounded worker budget, while nested worker work runs serially on its current host thread as logical worker 0. CPU native primitives now use that same scheduler owned by their `Program`, rather than a process-global worker pool. CUDA/AMDGPU initialization does not create a CPU worker pool. A shared compiled-graph JIT cache remains one consistent replay transaction. | Independent Python callers can safely share CPU native primitives, the scheduler, and graph-cache objects without overwriting another caller's state or oversubscribing a second primitive pool. The scheduler deliberately does not interleave two saturated jobs: production measurements did not justify that added complexity. One cached graph is still serialized for correctness, whereas distinct graph executables remain independently callable. |
| CPU native plain scatter | Defined plain scatter as a unique-target operation on the CPU native path. The implementation validates all in-range destination indices before writing and rejects duplicates; `scatter_add` remains the duplicate-target aggregation API. | A large duplicate-index scatter can no longer execute concurrent host `memcpy` operations to one target. Invalid requests fail before modifying the destination, while valid unique-target requests retain the native parallel path. |
| CUDA graph capture and graph run state | CUDA graph capture now passes its per-executable capture stream explicitly into CUDA kernel-module launches, rather than temporarily redirecting the current stream. Capture-owned argument buffers are retired on that same stream. Python graph runtime arguments are now per invocation; only the executable's mutable replay cache is shared and serialized. After Python arguments have been validated, native graph execution releases the GIL so concurrent callers reach that cache transaction instead of being accidentally serialized by Python. | Capture, recapture, and ordinary CUDA work no longer depend on a temporary global/TLS stream route. Reusing one graph with different ndarray arguments cannot overwrite another invocation's flattened arguments. One executable/cache is deliberately serialized for correctness; distinct executables may proceed independently. Existing graph replay remains ordered on the default CUDA stream; ordinary CUB/allocator calls also select that default stream explicitly outside capture. CUDA reset safely treats a runtime allocation already released by a live ndarray as absent during final cleanup. |
| Vulkan shared descriptor, pipeline-cache, and profiler state | Added owner synchronization for descriptor layouts/caches, default samplers, render-pass caches, and each native pipeline cache. Descriptor-pool allocation remains serialized by its pool, while descriptor updates and command-buffer binds are synchronized by the individual descriptor set. A command buffer pins every set it binds; a dirty resource set allocates a replacement instead of rewriting a set still recorded or in flight. Descriptor writes complete before cache publication; profiler scopes keep their query-pool token on the command list that opened them. | Concurrent Vulkan command recording and pipeline-cache snapshotting no longer race shared host-side containers or native cache handles, and independent descriptor-set updates do not wait on unrelated descriptor-cache or pool metadata. Reusing a resource set cannot silently change descriptors for already recorded GPU work. Interleaved profiler scopes report their own query results instead of accidentally closing another command list's scope. |
| Vulkan sparse SNode | Fixed early Forge Vulkan sparse SNode issues where inactive cell reads could return nonzero values and concurrent pointer-cell activation could lead to device loss. | MPM, SPH, sparse voxel, and brick-based rendering workloads get sparse data-structure semantics that are closer to CPU/CUDA. |

## Notes

- This page lists bug fixes only. Forge-only API and feature contracts are
  documented in their own pages.
- For Vulkan sparse SNode behavior, see [Vulkan sparse SNode](sparse_snode_on_vulkan.en.md).
- For public display-frame APIs, see [Display frame submission](display_frame.en.md).
- For native algorithm APIs, see [Native algorithms](native_algorithms.en.md).
- To collect repeatable Vulkan async-kernel/GGUI queue samples, run `tests/python/ggui_vulkan_queue_concurrency_stress.py` in fresh processes with `--warmup-seconds`, `--seconds`, and optionally `--offscreen` / `--output`. It reports frame-submit and sampled producer-submit p50/p95; it is a measurement tool, not a performance promise for a different GPU, driver, or window system.
