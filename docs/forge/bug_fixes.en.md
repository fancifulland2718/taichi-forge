# Taichi Forge Bug Fixes

## Fixed Issues

| Area | Fix | User impact |
| --- | --- | --- |
| ArgPack lifetime | Fixed premature Python GC of `ti.types.argpack(...)` objects while GPU kernels may still use their runtime allocations. See upstream [#8788](https://github.com/taichi-dev/taichi/issues/8788). | Long-running simulations, reinforcement-learning environments, graph replay, and high-frequency kernel launch loops no longer hit random crashes from ArgPack lifetime races. |
| ArgPack values on Vulkan | Fixed stale `ti.types.argpack(...)` reads on the Vulkan backend after repeated launches or updates to an existing ArgPack object. | Simulation, material, camera, and solver parameters passed through ArgPack now behave consistently across CPU, CUDA, and Vulkan without requiring user-side synchronization. |
| Vulkan small-integer fields | Fixed SPIR-V support for `ti.u8` / `ti.i8` / `ti.u16` / `ti.i16` fields on devices that expose the required Vulkan storage capabilities. See upstream [#8758](https://github.com/taichi-dev/taichi/issues/8758). | Color buffers, masks, voxels, compressed state, and image-like data can use small integer storage on the Vulkan backend. |
| Vector / Matrix ndarray release | Fixed runtime memory not being released when `ti.Vector.ndarray(...)` or `ti.Matrix.ndarray(...)` objects are destroyed. See upstream [#8763](https://github.com/taichi-dev/taichi/issues/8763). | Rendering staging buffers, particle buffers, and test loops that create temporary ndarrays no longer keep growing device memory. |
| Dense native paths after sparse SNode trees | Fixed CPU/CUDA native dense field paths, including `from_numpy()` / `to_numpy()` and native dense algorithms, after a sparse `pointer.bitmasked` tree had already been created. | MPM-style solvers can create sparse grids and then initialize or process later dense scalar, vector, or matrix fields without access violations or invalid CUDA copies. |
| PrefixSumExecutor warning | Fixed the AST warning caused by Python float division inside the internal scan kernel. See upstream [#8777](https://github.com/taichi-dev/taichi/issues/8777). | `ti.algorithms.PrefixSumExecutor`, compact, bucket builder, and other scan-based paths avoid a misleading compile warning. |
| GGUI `set_image()` staging | Optimized `canvas.set_image()` so CUDA/Vulkan Taichi field and ndarray images are packed to RGBA8 on the device, and contiguous host `uint8` RGBA NumPy images use the direct host RGBA8 path. | Rendering and simulation visualization avoid the old per-frame device-to-host staging round trip on the common device-image path. Packed `u32` display frames remain available for producers that already write final RGBA8 pixels. |
| GGUI event pump | Reduced headed GGUI mouse enter/leave overhead by preventing the ImGui GLFW backend from rewriting the native cursor every frame, and added `poll=False` to `Window.get_event()` / `Window.get_events()` so async render loops can drain events without a second `glfwPollEvents()`. | Async simulation/rendering loops can keep `window.show()` as the only per-frame event pump while preserving the legacy default behavior of event-reading APIs. |
| GGUI empty ImGui frames | Balanced the ImGui frame lifecycle when a frame has render work but no ImGui widgets: GGUI now calls `EndFrame()` for empty UI frames and skips backend ImGui draw submission. | Headed and offscreen GGUI loops can alternate widget and non-widget frames without hitting ImGui's "Forgot to call Render() or EndFrame()" assertion, while empty UI frames avoid unnecessary ImGui render commands. |
| GGUI hidden-window submission | Fixed a Windows/Vulkan crash that could happen when a hidden window completed one `canvas.set_image()` / `window.show()` frame and then released window resources. | Headless rendering, CI visualization smoke tests, and simulation screenshots can safely use `show_window=False`. |
| Vulkan async GGUI queue submission | Externally synchronized `vkQueueSubmit`, `vkQueueWaitIdle`, and `vkQueuePresentKHR` by the actual `VkQueue` handle, and protected per-thread stream creation and submission tracking. Compute and graphics streams share a lock only when they refer to the same Vulkan queue. | A Python worker can continuously submit Vulkan kernels while the main thread uploads and presents GGUI frames without racing host access to a shared queue. Applications do not need a coarse Python submission lock or an extra `ti.sync()` solely for queue safety; application-owned simulation/display data still needs an explicit producer-consumer protocol. |
| CUDA allocator capability and mapping lifecycle | Initialized CUDA memory-pool capability state and require both a CUDA 11.2+ driver and device memory-pool support before selecting async allocation. Internal CUDA buffer mapping now rejects invalid or repeated map calls and reliably releases host staging state during unmap, deallocation, or reset. | Older drivers and unsupported devices use the established synchronous allocation fallback instead of selecting an API from uninitialized state. Normal field and ndarray workflows retain their public API and synchronization semantics. |
| Vulkan pipeline-cache persistence | Reworked pipeline-cache snapshots to copy a complete, size-consistent blob and retry a transient `VK_INCOMPLETE`. A rejected or incompatible persisted cache is discarded and rebuilt from an empty cache instead of aborting initialization. | A stale `rhi_cache.bin`, including one left after a driver or device change, becomes a cache miss rather than a startup crash. Cache data remains an optional optimization and does not change kernel results. |
| Vulkan GGUI swapchain results | Explicitly classify successful, suboptimal, out-of-date, device-lost, and other present/acquire results. Suboptimal or out-of-date presentation schedules normal swapchain recreation on a later window frame, outside the Vulkan queue lock. | Resize, display-mode, and WSI transitions can drop a transient GGUI frame instead of presenting against stale resources. Device loss is reported once and is terminal for the current Vulkan program/window; recreate the program/window after addressing the underlying driver or device failure. |
| Vulkan sparse SNode | Fixed early Forge Vulkan sparse SNode issues where inactive cell reads could return nonzero values and concurrent pointer-cell activation could lead to device loss. | MPM, SPH, sparse voxel, and brick-based rendering workloads get sparse data-structure semantics that are closer to CPU/CUDA. |
