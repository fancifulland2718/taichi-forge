# Taichi Forge Bug 修复

## 修复概览

| 范围 | 修复内容 | 用户影响 |
| --- | --- | --- |
| ArgPack 生命周期 | 修复 GPU kernel launch 中 `ti.types.argpack(...)` 可能被 Python GC 提前释放的问题。参考上游 [#8788](https://github.com/taichi-dev/taichi/issues/8788)。 | 长时间仿真、强化学习环境、graph replay 或高频 kernel launch 中，ArgPack 参数包不再因异步执行和 GC 交错触发随机崩溃。 |
| Vulkan ArgPack 参数读取 | 修复 Vulkan 后端 `ti.types.argpack(...)` 在重复 launch 或修改同一参数包后，kernel 可能读到旧参数值的问题。 | 使用 ArgPack 传递仿真、材质、相机和求解器参数时，CPU、CUDA、Vulkan 行为更一致，不需要用户侧额外同步。 |
| Vulkan 小整数 field | 在支持相应 Vulkan storage capability 的设备上，修复 `ti.u8` / `ti.i8` / `ti.u16` / `ti.i16` field 在 SPIR-V 后端不可用的问题。参考上游 [#8758](https://github.com/taichi-dev/taichi/issues/8758)。 | 颜色 buffer、mask、voxel、压缩状态和图像类数据可以在 Vulkan 后端直接使用小整数存储。 |
| Vector / Matrix ndarray 释放 | 修复 `ti.Vector.ndarray(...)` 和 `ti.Matrix.ndarray(...)` 销毁后运行时内存不释放的问题。参考上游 [#8763](https://github.com/taichi-dev/taichi/issues/8763)。 | 高频创建临时 ndarray 的渲染 staging、粒子 buffer 和测试循环不再持续推高设备内存。 |
| sparse SNode 之后的 dense native 路径 | 修复 CPU/CUDA 后端在已经创建 sparse `pointer.bitmasked` tree 后，后续 dense field 的 `from_numpy()` / `to_numpy()` 和 native dense 算法可能使用错误地址的问题。 | MPM 风格求解器可以先创建稀疏网格，再初始化或处理后续 dense scalar、vector 或 matrix field，不再触发 access violation 或 CUDA invalid copy。 |
| PrefixSumExecutor warning | 修复 `PrefixSumExecutor` 内部 scan kernel 因 Python 浮点除法触发 AST warning 的问题。参考上游 [#8777](https://github.com/taichi-dev/taichi/issues/8777)。 | `ti.algorithms.PrefixSumExecutor`、compact、bucket builder 等依赖 scan 的路径减少误导性 warning。 |
| GGUI `set_image()` staging | 优化 `canvas.set_image()`：CUDA/Vulkan Taichi field 和 ndarray 图像会在 device 侧 pack 成 RGBA8，C-contiguous host `uint8` RGBA NumPy 图像会直接走 host RGBA8 路径。 | 渲染和仿真可视化中，常见 device 图像路径避免旧的每帧 device-to-host staging 往返。已经直接写最终 RGBA8 像素的 producer 仍可使用 packed `u32` display frame。 |
| GGUI 事件泵 | 降低可见 GGUI 窗口鼠标移入/移出时的开销：阻止 ImGui GLFW backend 每帧改写原生鼠标光标，并为 `Window.get_event()` / `Window.get_events()` 增加 `poll=False`，让异步渲染循环可以只 drain 队列而不再次调用 `glfwPollEvents()`。 | 异步仿真/渲染循环可以让 `window.show()` 成为唯一的每帧事件泵，同时保留事件读取 API 的旧默认行为。 |
| GGUI 空 ImGui 帧 | 修复有渲染工作但没有 ImGui widget 的帧生命周期：GGUI 现在会对空 UI 帧调用 `EndFrame()`，并跳过 backend ImGui draw 提交。 | 可见窗口和 offscreen GGUI 循环可以在有 widget / 无 widget 帧之间切换，不再触发 ImGui 的 "Forgot to call Render() or EndFrame()" assertion，同时空 UI 帧不会产生不必要的 ImGui 渲染命令。 |
| GGUI 隐藏窗口提交 | 修复 Windows/Vulkan 隐藏窗口完成一次 `canvas.set_image()` / `window.show()` 后，进程退出或窗口资源释放阶段可能崩溃的问题。 | headless 渲染、CI 可视化 smoke test 和仿真截图路径可以安全使用 `show_window=False`。 |
| Vulkan 异步 GGUI queue 提交 | 按实际 `VkQueue` handle 对 `vkQueueSubmit` 和 `vkQueuePresentKHR` 做 external synchronization，并保护逐线程 stream 创建和提交追踪状态。stream 同步现在只等待该 stream 已提交的 fence，且等待时不持有 queue lock；profiler query 结果会绑定到实际成功提交它的 fence。共享 fence 的 host access 也会串行化。 | Python worker 可以持续提交 Vulkan kernel，同时由主线程上传并 present GGUI 帧，不再并发访问同一个 queue。同步一个 stream 不会再把无关的 queued compute、graphics 或 present 工作拖入 queue-wide idle。应用不需要仅为 queue 安全增加粗粒度 Python submission lock 或额外 `ti.sync()`；应用自己持有的仿真/显示数据仍需明确的 producer-consumer 协议。 |
| CUDA target 解析与 cache 隔离 | 将 CUDA 物理设备计算能力与 LLVM NVPTX 实际代码生成 target 分离。resolver 使用随附 LLVM 支持的 processor/PTX 配对；CC 12.0 设备会选择原生 `sm_120` / PTX 8.7，其它设备则选择不高于设备能力的最高兼容 compiler target。CUDA offline cache key 现在也包含该解析后的 target。 | 新架构 GPU 在随附编译器已经支持原生 target 时，不再被报告或编译为旧 `sm_86` fallback。尚无 compiler target 的未来 GPU 会安全使用最高兼容 target，且不会复用为其它 target 生成的 PTX cache。公开的 `cuda_compute_capability` 查询现在返回真实设备能力。 |
| CUDA native runtime 版本解耦 | 移除 CUDA 13.2 专属 `<cuda/iterator>`，改用轻量 device iterator；native loader 不再仅因 driver 报告的同一 CUDA major minor 较低而提前拒绝。发行仍保持每个系统一个 `taichi-forge-runtime` wheel，包内清单声明并校验唯一的动态 CUDART major。 | 用户仍只需安装 `taichi-forge`，无需选择 `cu11` / `cu12` / `cu13` 包或本机 Toolkit。当前 workflow 默认构建基线仍是 CUDA 13.2；只有较低 Toolkit wheel 在目标旧驱动和 Linux manylinux 上通过后，才会降低对外驱动门槛。 |
| CUDA contention 与 allocator 诊断 | 在既有 CUDA Driver 和 context lock 外围增加采样式、非阻塞 contention counter，并记录 async pool allocation/free 调用和同步 fallback。`cuda_driver_telemetry_stress.py` 会以原子结果校验运行 1/2/4 个 Python submitter。 | 同步语义没有改变：这些 counter 只在改变 lock topology 前提供证据。它们可以显示 workload 是否真的竞争 host lock、临时 allocation 是否走 async pool 或安全 fallback，且不在每次调用读取时钟，也不增加 `ti.sync()`。 |
| CUDA void kernel launch allocation | CUDA LLVM launcher 现在只在 kernel 返回值或 host array transfer 真正需要时分配 device result buffer；只操作 Taichi field 的 void kernel 不会分配该 buffer。 | 常规 field-only CUDA submission 不再每次创建一对 stream-ordered async allocation/free。返回值和 host array copy 保持原有 result channel 与顺序；此改动不增加跨 invocation 的常驻 buffer、额外同步，也不改变 graph capture/replay 的所有权。 |
| CUDA 版本宏与随附 libdevice | 将生成的字符串宏 `CUDA_VERSION` 改为 `TI_CUDA_LIBDEVICE_VERSION`，并从构建实际打包的唯一 `slim_libdevice.<major>.bc` asset 推导其值；安装阶段也使用同一个已发现的 asset。 | Taichi 不再覆盖 NVIDIA CUDA header 中表示 toolkit 数值版本的 `CUDA_VERSION` 宏，消除宏重定义的构建风险。`core.cuda_version()` 保留既有字符串形式，但明确表示随附 libdevice 的兼容版本，而不是本机 CUDA Toolkit 或 GPU driver 版本；wheel 因而可在受支持的 driver/toolkit 间保持可移植性。 |
| CUDA allocator capability 与映射生命周期 | 初始化 CUDA memory-pool capability 状态；只有 driver 为 CUDA 11.2+ 且设备声明支持 memory pool 时才选择 async allocation。内部 CUDA buffer mapping 现在会拒绝无效或重复 map，并在 unmap、dealloc、reset 时可靠释放 host staging 状态。 | 旧 driver 或不支持的设备继续走既有的同步分配 fallback，不会因未初始化状态选择错误 API。普通 field 与 ndarray 工作流的公开 API 和同步语义不变。 |
| CPU/CUDA allocation identity 与生命周期 | 将 CPU/CUDA 内部可变 allocation table 替换为带 generation 校验、record 地址稳定的实现。每次 allocation、copy、map、readback 都会验证所属 device 与无溢出的完整范围，并在操作期间持有短生命周期 lease；stale、已释放、错误 device、越界的 handle 会被拒绝。CUDA async allocation 会保存其分配 stream，用于 stream-ordered 释放；每条 allocation 独立持有 mapping state。 | 多个 host 调用者不再竞争 vector 扩容，也不会访问已经被复用的 allocation record。这不等于串行化应用对同一 field/buffer 的冲突写入，也不会创建跨 stream 数据依赖；共享数据的所有权和顺序仍必须由应用显式表达。 |
| Vulkan-CUDA external-memory 生命周期 | Vulkan device 只有在同时启用 external-memory 基础能力与平台句柄扩展时，才声明可导出外部内存。interop cache 以 Vulkan allocation generation 为 key，并在 allocation/device teardown 时释放；interop copy 会在可回收 imported mapping 前完成对应 CUDA 工作。 | 在支持的 Windows/Linux 设备上，直接 Vulkan-CUDA buffer copy 不再在 allocation 复用或 teardown 后保留 stale imported mapping。缺少平台导出扩展的设备会安全回退到同步 host staging，不会调用不可用的 handle-export 函数。这个保守的完成等待只作用于 interop transfer 路径；普通 CUDA kernel 与 Vulkan submission 仍保持异步。 |
| Vulkan pipeline-cache 持久化 | pipeline cache snapshot 改为复制完整且 size 一致的 blob，并对瞬时 `VK_INCOMPLETE` 重试。持久化 cache 被驱动拒绝或不兼容时会安全丢弃，并从空 cache 重建，不再中止初始化。 | 旧 `rhi_cache.bin`，包括 driver 或设备切换后留下的文件，会退化为 cache miss 而不是启动崩溃。cache data 仍只是可选优化，不改变 kernel 结果。 |
| Vulkan GGUI swapchain 结果处理 | 显式分类 success、suboptimal、out-of-date、device-lost 与其他 acquire/present 结果。suboptimal 或 out-of-date 只会在后续窗口帧安排正常的 swapchain 重建，且不在 Vulkan queue lock 内重建。 | resize、显示模式或 WSI 变化时，GGUI 可以丢弃一个瞬时帧，而不会向失效资源 present。device lost 只报告一次，并对当前 Vulkan program/window 视为终止性错误；处理底层 driver 或设备问题后应重建 program/window。 |
| CPU 并发 job、native primitive 与 cached graph replay | CPU scheduler 的每次 submission 独占 callback、context、completion 和 exception 状态。并发 producer 进入公平 FIFO 队列；一个 active job 使用其请求且受总预算约束的 worker，worker 内嵌套工作仍在当前宿主线程以逻辑 worker 0 串行完成。CPU native primitive 现在使用所属 `Program` 的同一 scheduler，不再使用进程级全局 worker pool。CUDA/AMDGPU 初始化不会创建 CPU worker pool。共享 compiled-graph JIT cache 仍以完整 replay 事务执行。 | 独立 Python 调用者可以安全共享 CPU native primitive、scheduler 与 graph cache，不会覆盖其他调用者状态，也不会因第二套 primitive pool 超出线程预算。scheduler 有意不交错两个饱和 job：生产型测量不足以证明这部分复杂度有价值。同一个 cached graph 仍为正确性串行；不同 graph executable 可独立调用。 |
| CPU native 普通 scatter | 将 CPU native plain scatter 定义为 unique-target 操作。实现会在写入前验证所有有效 destination index，并拒绝 duplicate；`scatter_add` 仍是支持 duplicate target 的聚合 API。 | 大规模 duplicate-index scatter 不会再对同一目标并发执行 host `memcpy`。无效请求会在修改 destination 前失败；合法的 unique-target 请求仍保留 native 并行路径。 |
| CUDA graph capture 与 graph run state | CUDA graph capture 现在将每个 executable 自己的 capture stream 显式传给 CUDA kernel module launch，不再临时重定向 current stream。capture-owned argument buffer 也在同一 stream 上退役。Python graph runtime argument 改为每次 invocation 独立持有；只有 executable 的可变 replay cache 仍被共享并串行化。Python 参数校验完成后，native graph execution 会释放 GIL，让并发调用者真正进入该 cache transaction，而不是被 Python 意外串行化。 | capture、recapture 与普通 CUDA 工作不再依赖临时的 global/TLS stream 路由。复用同一 graph 但传入不同 ndarray 时，不会覆盖另一 invocation 的 flattened argument。同一 executable/cache 为正确性刻意串行；不同 executable 可以独立推进。现有 graph replay 仍在 default CUDA stream 上保持顺序；普通 CUB/allocator 调用也会在 capture 之外显式选择该 default stream。CUDA reset 最终清理时，若 live ndarray 已经释放 runtime allocation，会安全地把该 allocation 视为不存在。 |
| Vulkan descriptor、pipeline cache 与 profiler 共享状态 | 为 descriptor layout/cache、default sampler、render-pass cache 和每个原生 pipeline cache 增加 owner 同步。descriptor-pool allocation 仍按其 pool 串行；descriptor update 与 command-buffer bind 则按单个 descriptor set 同步。command buffer 会 pin 每个已 bind 的 set；dirty resource set 遇到仍在 recorded 或 in-flight 的旧 set 时会分配替代 set，而不是原地改写。descriptor write 完成后才发布到 cache；profiler scope 的 query-pool token 归属开启它的 command list。 | 并发 Vulkan command recording 与 pipeline-cache snapshot 不再竞争共享 host 容器或 native cache handle；互不相干的 descriptor-set update 不再等待 descriptor-cache 或 pool metadata。复用 resource set 不会悄悄改变已记录 GPU 工作使用的 descriptor。交错的 profiler scope 会读取自己的 query 结果，不会误关闭另一 command list 的 scope。 |
| Vulkan sparse SNode | 修复 Forge Vulkan sparse SNode 早期的 inactive cell 读值不为零，以及 pointer cell 并发激活后可能 device-lost 的问题。 | MPM、SPH、稀疏体素和 brick-based 渲染工作负载在 Vulkan 上获得与 CPU/CUDA 更一致的稀疏数据结构语义。 |

## 说明

- 本文只列 bug 修复，不列 Forge-only 功能介绍。功能合同见对应专题文档。
- Vulkan sparse SNode 的完整语义和限制见 [Vulkan 稀疏 SNode](sparse_snode_on_vulkan.zh.md)。
- 显示帧提交相关公开入口见 [显示帧提交](display_frame.zh.md)。
- native 算法相关入口见 [Native 算法](native_algorithms.zh.md)。
- 单 runtime wheel 与内部 CUDA 构建基线的发行合同见
  [构建 Wheel](build_wheels.zh.md)。
- 尚待 Linux release 复测的项目（包括随附 libdevice 映射和 Vulkan-CUDA fd interop）见
  [Linux 复测清单](linux_revalidation.zh.md)。
- 如需采集可重复的 Vulkan async-kernel/GGUI queue 样本，请在 fresh process 中运行 `tests/python/ggui_vulkan_queue_concurrency_stress.py`，并使用 `--warmup-seconds`、`--seconds`，以及可选的 `--offscreen` / `--output`。它会报告 frame-submit 和采样 producer-submit 的 p50/p95；这是测量工具，不对不同 GPU、driver 或 window system 作性能承诺。
